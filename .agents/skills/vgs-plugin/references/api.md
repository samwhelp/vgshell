# Plugin API

What a plugin receives and may call. The core owns every table here; a value not listed does not exist for a plugin.

## Kinds

| Kind | Entry point key | Base | Host today | Built when |
|---|---|---|---|---|
| `bar-widget` | `bar-widget` | `BarWidget` from `qs.Ui` | the active bar's sections | placed in `bar.layout.<section>`, not in `disabledPlugins`, and a bar is active |
| `bar` | `bar` | `Item` declaring the three section containers below, and optionally `property bool shown`: the host maps no surface on a screen while the bar there declares it false, and an unmapped bar reserves no space; declare it false while the bar has nothing to draw | the bar host, one per screen | it is `bar.id` in the configuration and is not in `disabledPlugins` |
| `service` | `service` | `Item` | the service host | enabled |
| `background` | `background` | `Item` declaring `property var screen: null`, and optionally `property bool shown`: the host maps no surface on a screen while every instance there declares it false; declare it false while the background has nothing to draw | the background host, one per screen, under every window | enabled |
| `cover` | `cover` | `Item` declaring `property var screen: null`, and `property bool shown`: the host maps no surface on a screen until an instance there declares it true | the cover host, one per screen, above every window with exclusive keyboard focus while mapped | enabled |
| `panel` | `panel` | `Item` with `open(payloadJson)` and `close()`, optional `initialFocus`, sized by `implicitWidth` and `implicitHeight` | the panel host: a popup under its anchor item with a focus grab, or a layer surface on the top layer without one, centred on the whole monitor by default | enabled and summoned, until hidden |
| `overlay` | `overlay` | `Item` with `open(payloadJson)` and `close()`, optional `initialFocus` | the overlay host: an anchored popup, or a layer surface covering its screen without an anchor | enabled and summoned, until hidden |
| `menu` | `menu` | `Item` with `open(payloadJson)` and `close()`, optional `initialFocus`, sized by `implicitWidth` and `implicitHeight` | the menu host: a popup under its anchor item with a focus grab, or a layer surface on the overlay layer without one | enabled and summoned, until hidden |
| `window` | `window` | `Item` with `open(payloadJson)` and `close()`, optional `initialFocus`; the first width follows `implicitWidth`, and the first height takes the larger of `implicitHeight` and its outer titled window `Pane` content, capped by the output's room; the item fills the window after | the window host: a Hyprland window titled with the manifest's `name`, floating and centred, with or without an anchor | enabled and summoned, until hidden or closed through Hyprland |
| `pane` | `pane` | `Item` with `open(payloadJson)` and `close()`, optional `initialFocus` and `footer` Item, filling the holder's container: a body with no `Pane` and no title, its content from x 0 and its height its `implicitHeight`; the holder draws the title, owns the inset and scrolls the body; the pane owns its optional footer item, which the holder places in its shared `Pane.footer` outside the scrolling body | the enabled holder of capability `panes`, one pane at a time | enabled and mounted by that holder |

`PluginLogic.isEnabled` is the judge of enabled, and its comment states the rule.

A summoned kind is built on summon and destroyed on hide. An entry may implement `holdsHide()`: `hide` asks it first, and an entry that answers true stays open, as the Settings window does while it asks about an unsaved edit. `open(payloadJson)` that throws refuses the summon with `refused: open-failed=<id>`, so a payload that does not parse is left to throw. Summoning an open one calls `open` again with the new payload. After `open()` returns, the host focuses the entry's optional `initialFocus` item with `Qt.OtherFocusReason`, so initial focus draws no keyboard ring. Without `initialFocus`, the host slot keeps focus so Escape still reaches it and Tab enters the plugin's chain. Pass the item the surface belongs to as `anchor`. The compositor places an anchored surface beside that item in its own window and adjusts it at screen edges. Moving the item moves the popup. An anchored surface takes keyboard focus and closes on a click outside, receiving `close()`. The popup also closes when its anchor is hidden or destroyed. A panel or menu summoned without an anchor sits at its `placement` setting: `top-left`, `top`, `top-right`, `left`, `center` (the default), `right`, `bottom-left`, `bottom` or `bottom-right`. `center` ignores the space a bar reserves and centres on the whole monitor; every other placement keeps clear of it. A panel or menu summoned without an anchor closes on a press beside it over a client window or the empty desktop of any screen too, receiving `close()`; a press on a bar leaves it open, except at the `center` placement, whose layer covers the bar. An overlay owns a press beside its content on its own screen; an overlay entry that implements `pressedOnOtherScreen()` hears a press on any other screen through it, as the Launcher closes, and without it the other screens take their presses as before. A `window` ignores the anchor and `placement`: Hyprland maps it on the focused monitor, draws its border, focuses it and moves, tiles and closes it like any other window, and a close there calls `close()`. An Escape no item of the plugin accepts while a summoned panel, menu, overlay or window has the keyboard closes it the same way; accept Escape only for a step of the plugin's own, such as popping a page. It draws no frame of its own. Pick `window` for a surface the user works in; a flyout is an anchored `panel` or `menu`; content that sits over every window and never takes the keyboard goes on the passive layer of capability `layers`. `PluginLogic.summonSurface` decides the surface class: [D044](../../../../docs/decisions/D044-application-windows-are-hyprland-toplevels.md), [D018](../../../../docs/decisions/D018-overlays-are-quickshell-popups.md).

## Properties every instance receives

| Property | Type | Assigned by | Meaning |
|---|---|---|---|
| `shell` | object | the core, after creation and again when the plugin's settings change | this plugin's scoped object, table below |

Declare it as `property var shell: null`, or inherit it from `BarWidget`.

## Properties a bar widget also receives

| Property | Type | Meaning |
|---|---|---|
| `bar` | object | the bar API below |
| `moduleName` | string | the plugin id; the core assigns it after creation |
| `settings` | object | the manifest's `settings` under the widget's layout entry, for example `{ "units": "metric" }`; the entry id is excluded; reassigned when the entry changes |
| `frame` | object | what `BarWidget`'s right-click Hide reads and calls; a widget reads nothing from it |

`BarWidget` adds `barSize`, `setting(name, fallback)` and `frameActions`, a list of `{ label, icon, action }` the widget's right-click menu shows after Hide.

## Properties a bar also receives and declares

| Property | Direction | Type | Meaning |
|---|---|---|---|
| `screen` | received | ShellScreen | the screen this bar draws on |
| `leftSection`, `centerSection`, `rightSection` | declared | Item | passive containers with a `spacing` property from the bar's gap token; the core binds their implicit width and each child's position and size. A section the bar scrolls also declares `viewX` and `viewWidth`, the box it draws in, and `shownX` and `shownWidth`, the part that shows whole widgets, in its own coordinates, `settledX`, the x it comes to once a scroll it slides to has ended, `reveal(item)` and `step(direction)`, one widget toward its start (-1) or its end (1): a drop over that box lands in that section beside the shown widgets, read from where the section settles, the core reveals the preview gap and the dropped widget, and while a dragged widget is held past the shown widgets at an end that hides some, the core calls `step` every `bar.scroll.hold` milliseconds |
| `builtinNames` | declared | list of strings | registration names the bar can draw, accepted only under the active bar's ID |
| `builtinFamilies` | declared | list of strings | optional families the bar draws once per layout entry: each entry `<bar id>/<family>-<n>`, n from 1, is one more registration name |
| `builtinLabels` | declared | object of labels keyed by registration name | labels for the builtin placement fields on the bar's Settings page, including hidden builtins |
| `widgetLayout` | received | object | the effective `left`, `center` and `right` entry lists; the bar uses the registered IDs to keep its builtin model current |

A bar never creates, destroys or reads a plugin widget. It draws its own builtins from `widgetLayout` and registers each wrapper with `shell.builtins`. The core orders registered builtin IDs and plugin IDs together through `bar.layout`. A builtin wrapper extends `BarWidget`, gives its label through `Accessible.name` and receives the shared drag and Hide callbacks in `frame`. Hide removes its ordinary layout entries without changing its owner's settings or enablement. Its model owns its lifetime and preserves the same object across section moves. A built-in widget is drawn by its plugin inside its own surface and is never a kind ([D005](../../../../docs/decisions/D005-kinds-are-surfaces-no-dependencies.md)).

The Settings page draws each displayable entry read-only as a Status row on Details, but for a list of stored keys, which it draws on the Settings tab, one line per key: the `presenceList` of a manifest that declares `secrets`, with each key's steps, or a `presenceList` whose `group` is `Setup`, for keys the plugin stores through its own setup screen; a list of another group draws in that group's own section with the group's `state` entries, which then leave Details; `hidden` keeps one off, and a `state` value of `{ "hidden": true }` alone keeps its row off while the writer has nothing to show. An action declares exactly one route: `tui` for its own declared script, `install` for its own requirements, `system` or `undo` for a declared system step, or `dictation: "setup"` for a holder of capability `dictation`. An entry's `action`, or the one of a `state` entry's `actions` its value names, is a one-click setup step the page draws only while the published value calls for it: a `presence` while `absent`, a `state` while its `action` is true or a name. An action that removes what the user set up, such as a sign-out, carries `tone: "danger"` and draws in the danger style. |
| `secrets` | no | `{ service, label }`: the libsecret items the core stores, replaces and clears for the plugin from a masked field in the Setup section of its Settings page. Each account is the `secret` of a `presenceList` status item, and the plugin never sees the value. |
| `hyprland` | no | What the plugin asks of Hyprland, as data the core renders into the one Hyprland layer: [hyprland.md](../../../../docs/architecture/hyprland.md). `binds`: each shortcut the plugin registers through capability `shortcut`, with its default key, a non-empty list of keys that each get a bind, or `null` for none, which the Settings page's Keys row lets the user replace; `hold` adds a release bind, `tap` fires on a tap of a lone key, `info` explains it behind an info icon. `layerRules`: blur and alpha rules for the core hosts' `^vgs:<name>$` namespaces. `appearance`: below. `options`: maps a schema setting to a Hyprland input option, written only while the plugin's `plugins` row sets that setting; capability `hyprland` reads it back. `pads`: a `list` setting whose items are pads, each bound as `pad-<name>` with no key by default; `shell/Core/Pads.js` states the fields. `monitors`: the one setting that stores monitor rules, owned by one enabled plugin. |
| `requirements` | no | The external commands and D-Bus names the plugin uses, each with its package per manager, `optional` when the plugin works without it, a one-line `purpose` and, for a command, an optional `floor`: the lowest version the plugin works with, three dotted numbers. The core reads the version an enabled plugin's command prints for `--version`, and one below its floor is `outdated`. The Settings page lists each with its state and offers Install all missing while one is missing, and Update all outdated while the rest are only outdated. |
| `tui` | no | Floating TUI scripts under the plugin's `tui/`, opened with `shell.tui.run`; an `entry` draws one as a Setup action: [commands-are-data.md](../../../../docs/architecture/commands-are-data.md). |
| `menu` | no | Launcher rows keyed by a dotted id whose dots name its parent. A row runs one of the plugin's shortcuts (`shortcut`), opens a listed TUI (`tui`) or the first TUI of a group (`tuiGroup`), or is a category without them. `provider` fills a category from a `launcherRows` status entry; selecting a published row calls the shortcut with that row's id. `toggle` shows its own label and icon while its boolean setting is true, so the label always names what selecting the row does. The launcher lists every enabled plugin's rows through `shell.shortcut.menu`. |
| `systemSteps` | no | The core's system steps the plugin offers; a status action `{ label, system }` applies one: [commands-are-data.md](../../../../docs/architecture/commands-are-data.md). |

A `schema` entry or drawn `status` entry may declare `info`, one printable explanation. The Settings page draws an info icon beside that row and opens the explanation in a dialog.

### Settings schema

The Settings window draws one field per entry in key order, ungrouped entries first, then each `group` in the order its first entry appears. A boolean uses a switch. An enum with at most three options uses a segmented control, and a larger enum a select. A string with `optionsFrom`, or a string or number with `presets`, uses a select, which adds Custom… when `allowCustom` is true. A bounded number uses a slider. A `unit` of `seconds`, `minutes`, `hours` or `days` shows the largest whole unit; `%` and `×` are drawn after the number. `format: "datetime"` previews a Qt date and time format. A `list` has its own section; when it names a group that exists, that section follows the group, else it stays after the grouped fields. `shell/Core/Pads.js` judges its items.

A flat entry's `link`, `{ text, url }` or `{ text, pane }`, draws `text`, words its `description` holds, as a link that the pointer, Return, Enter and Space open: `url` in the default browser, `pane` as that plugin's page in the panes holder. `url` is an https address with a host and no user part; the judge refuses any other scheme. `pane` is a plugin id; the judge refuses a link with both or neither. A key field names where to get its key this way, never as an address to copy. A drawn `status` entry may declare a `url` link over words of its `hint`, for a step the user takes on a web page.

`optionsFrom` names a `choices` status entry of the same plugin, and the select offers its published choices. The first offer stands for the empty string and reads as its own label, so the plugin offers first what "" resolves to; for an entry that declares `placeholder`, "" means nothing is chosen: no offer stands for it, and the select reads that text. The core delivers and stores the configured string unchanged. A configured value no longer offered stays stored and shows as unavailable, or under Custom… when the entry declares `allowCustom`. An entry that declares `hideEmpty: true` is not drawn while nothing is offered for it, whatever is stored; a `list` item field may not declare it. A status update never writes a setting. A plugin that reads its choices on demand registers `shell.status.handleRefresh` for the entry; the Settings page calls it each time the select opens, and the list follows the plugin's next publish.

### Hyprland appearance

`hyprland.appearance` is an object for a plugin that has capability `theme`. It maps `noGaps` to a boolean setting key in the same manifest schema. The first enabled plugin by id that declares appearance owns the switch. A later declaration is reported as a Hyprland problem and ignored. The core's default is no gaps off. The theme's borders, radius and motion follow the user's Appearance values instead (capability `appearance`): each holds over a user's own Hyprland lines unless the user keeps their own value, and window animations are written only once the user turns them on. `noGaps` writes zero gaps as a workspace rule, which holds over a user's later `general` gaps; only a later workspace rule that sets gaps overrides it.
