# Update pipeline

The plugin declares two floating TUIs that update.

- `update` runs `tui/update.sh`: every source in one run. The plugin's Packages category in the launcher opens it.
- `update-source` runs `tui/update-source.sh <source>`: one source. `<source>` is a status row's `source`: the primary package manager's id, `aur`, `flatpak`, `mise`, `vgs`, `plugins` or `themes`. It is not listed, because it needs its argument: `shell.tui.run("update-source", [source])` opens it.

Both take `-y`, which skips the start question only. They share `tui/pipeline.sh`, whose header is the full contract. A run takes these steps in this order:

1. The log and the lock. `script` writes the run to `${XDG_STATE_HOME}/vgshell/updates/update.log`. The lock is `${XDG_RUNTIME_DIR}/vgs-tui-updates.lock`. A second run exits 75 and leaves the first run's log as it is.
2. A warning when `/` has less than 10 GiB free.
3. The plan box: the snapshot tool, each source with the commands it runs, and the log path. Then `Start the update?`, unless `-y`.
4. The review of third-party packages, when `reviewThirdParty` is on: [§ Third-party review](#third-party-review).
5. One sudo session, when a snapshot or the system step needs root and the elevation command is `sudo`. `vgshell pkg run` joins it, so the password is asked once. The elevation command is the one `vgshell pkg plan upgrade <primary>` names: `packages.elevate` in `shell.json`, else the first of `sudo`, `doas` and `run0` on `PATH`. `doas` and `run0` ask as their own rules say.
6. A snapshot through snapper, else timeshift, behind the elevation command. It comes before any step that replaces a package: the system upgrade, the AUR upgrade or the `vgshell-git` rebuild. No snapshot is taken when the `snapshot` setting is `off`, when neither tool is on `PATH` or when no elevation command resolves. The plan box says which. A tool that fails or has no configuration prints a warning, and the update continues without a snapshot.
7. VGS itself: `vgshell self update` for a checkout or a curl install. It restarts a running shell. The `vgs` package updates with its package manager, and a Nix tree with its flake.
8. The system: `vgshell pkg run upgrade --manager <primary>`.
9. Flatpak and mise: `vgshell pkg run upgrade --manager flatpak`, then `--manager mise`.
10. Each plugin, then each theme, that is behind its upstream: `vgshell plugin update <id>` and `vgshell theme update <name>`. Each shows its diff and asks `[y/N]`. The pipeline passes `--yes` only when `trustPluginUpdates` is on. A declined update reads skipped in the result list, and the run continues.
11. The end of the sudo session. The credential is dropped.
12. The AUR, last: the `aurCommand` setting's words, else `vgshell pkg run upgrade --manager aur` (`paru -Sua` or `yay -Sua`). No AUR build runs under the update's credential. When VGS is the `vgshell-git` package and behind, `<helper> -S vgshell-git` follows, because an AUR helper rebuilds a `-git` package only when its recipe's version changes. The helper asks `sudo` itself. The credential it caches is dropped when this step ends, fails or is interrupted.
13. On pacman, after a system or AUR upgrade, the orphaned packages from `pacman -Qtdq`, with `Remove N orphaned package(s)?`, default no. A yes runs `vgshell pkg run remove --manager pacman`.
14. A shell restart, when a package step or the `vgshell-git` rebuild replaced the VGS package.
15. The result list, `Update result`: one line per step of 7 to 10 and 12 and per package the review skipped, `<item>: installed`, `<item>: skipped, <reason>` or `<item>: failed, <cause>`.
16. A reboot question, `Reboot` or `Later`, default Later, when the run changed a package that takes effect after a reboot, or the kernel or the running Hyprland binary was replaced (`vgs_tui_reboot_check`). On pacman the run reads `pacman -Q` before its first package step and after its last. A package whose version changed, or a new one, takes effect after a reboot when CachyOS's reboot hook, `usr/share/libalpm/hooks/cachyos-reboot-required.hook` under pacman's `RootDir`, names it for that operation and the hook script's conditions hold: an NVIDIA module only for the running kernel, and a file system tool only while its file system is mounted (`UpdatesLogic.rebootPackages`). Without the hook no package does. The Reboot notice setting VGS only turns the CachyOS notice off, so this question is the only one, and the run still reads the hook. A yes runs `systemctl reboot`.

Every package step is the package table's own plan, from `vgshell pkg plan upgrade <id>`. The steps take no `-y`, so each manager asks its own questions in the terminal. A package source without an upgrade plan, such as `nix`, is left out of the run with the reason in the plan box.

With `-y`, the orphan list and the reboot reason are printed instead of asked. The review's questions are still asked.

A failing step of 7 to 10 or 12 records its cause, else `exit <n>`, and the run goes on with every later step. The cause is the last line the step printed on stderr; after a VGS refusal line, `vgshell: refused:` or `vgs-tui: refused:`, it is the last line after the refusal, else the refusal's value, except after `vgshell pkg run`'s closing `rescan=` refusal, where it is the package manager's last line before it. A step whose stderr ends on an unanswered `[Y/n]` or `[y/N]` question, or a declined plugin or theme update, reads skipped, you declined it. After a failed or declined system step, the AUR step and the `vgshell-git` rebuild do not run and read skipped, since AUR packages build against the system that step left; every other step still runs. A run with a failed step says so after the result list and exits 1 after the reboot question. A step a Ctrl-C ends stops the run with 130. Any other failing step stops the run: the terminal shows `updates: failed exit=<n> log=<file>` and how to recover. The sudo session, or the guard around the AUR, drops the credential on the way out.

The TUIs read the plugin's settings with `vgshell plugin settings vgs.updates`, since `shell.tui.open` hands a script no arguments. `bin/facts` reads each `vgshell` JSON answer for the shell script. It decides whether VGS, a plugin or a theme is behind through `UpdatesLogic.js`, as the service does.

When a run ends, the service checks again ([developer.md § Cadence](developer.md#cadence)).

## Third-party review

When `reviewThirdParty` is on, an AI agent reviews the packages from outside the distribution's official repositories before any step installs them. The review covers pacman systems only.

- **The agent.** `reviewCommand`, when set, runs as written: its words split on spaces, never through a shell. When it is empty, the agent `reviewAgent` names runs, else the first one on `PATH`, `claude` before `codex`, each with its default command. `UpdatesLogic.REVIEW_AGENTS` holds the table and `UpdatesLogic.reviewPlan` the choice. Each default command asks before the agent runs a command and keeps its writes to the review directory. With no agent found, or a chosen agent, or an agent the command names, that is not installed, the run takes no review.
- **The packages.** The AUR's pending updates from `vgshell pkg check --json --source aur`, when the run takes the AUR through paru or yay; through another helper the AUR is not reviewed, and the plan box says so. `vgshell-git`, when the run rebuilds it. The system's pending updates from `vgshell pkg check --json --source pacman` that a repository of `pacman-conf --repo-list` holds, by `pacman -Sl <repository>`, when that repository is not official: `core`, `extra`, `multilib` and each `cachyos*` repository are (`UpdatesLogic.officialRepository`). Each such repository's servers, without any credentials in the URL, and signature level come from `pacman-conf --repo`. With nothing pending, no review runs.
- **The plan box** names the agent and the packages. A list that cannot be read is named there too, and counts as no verdict.
- **The install scripts.** After the fetch, the run judges each AUR package's install script by its change against the installed package's: `UpdatesLogic.installScriptChange` through `bin/facts install`. The new script is the file the `install =` line of the package's `.SRCINFO` names; the installed one is `<DBPath>local/<package>-<version>/install`, `DBPath` from `pacman-conf DBPath` and the version from the pending update, or `pacman -Q` for `vgshell-git`. The package's folder is the one whose `.SRCINFO` has its `pkgname` line, since `-G` saves a split package under its base, and its `install =` line is its own section's, else the base section's. The fetched tree is untrusted: the run reads a `.SRCINFO` or a script only when it is a regular file, not a link, and writes nothing into the tree. It adds `install <package> none|new|unchanged|changed` to `packages.txt` and, for `changed`, writes `install/<package>.diff` in a 0700 directory it makes. A package whose folder is not found, or whose script is a link, not a regular file or cannot be read, reads `install <package> unread` and is flagged. Each risky line the update adds, such as a setuid or setgid mode, a new group or a download (`UpdatesLogic.INSTALL_SCRIPT_RISKS`), flags the package whatever the agent's verdict, so a risk the installed package already carried is not flagged again.
- **The window.** After the start question and before the sudo session, the run makes the stable start directory `${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/vgshell/updates/review`, mode 0700, and then makes the per-run directory `<start>/<pid>`, mode 0700, by an exclusive `mkdir`. Claude Code keys folder trust on the directory it starts in, so the stable path makes the user trust it once ([Claude Code permissions](https://code.claude.com/docs/en/permissions)). It writes `command`, one word a line, and `packages.txt` into the per-run directory, fetches the AUR build files with `<helper> -G <package>...` into `<dir>/build/`, as the user, and calls `vgshell ipc call vgs.updates invoke review <dir>`. The service opens the `review` TUI, `tui/review.sh <dir>`, with `shell.tui.run`, and writes `<dir>/ended` with the run's code when it ends, only while the directory is there. That run's end starts no update check: the update run's own end does. `tui/review.sh` holds `<dir>/review.lock`, writes `<dir>/started` and runs the command with the text of `review/third-party.md` as its last argument, from the stable start directory. The prompt names `<dir>`, where the agent writes `verdict`. The agent has no install step and no elevation.
- **The wait.** The run waits up to 60 s for `started` or `ended`, then for the lock, which is free once the agent exits or the user closes the window.
- **The verdict.** The agent writes `<dir>/verdict`: `verdict clean`, or `verdict flagged` and one `flag <package> <concern>` line per flagged package. `UpdatesLogic.parseVerdict` judges it. A clean verdict covers the packages listed, and the run goes on. No verdict file, or any other text, asks `Continue without a review?`, default no, and a no stops the run, which exits 0. Then each package the agent or the install script check flagged shows its concerns and asks once, `Skip <package>, or install it anyway?`, with `Skip`, the default, and `Install anyway`. Skip keeps the package out of its upgrade step and out of the `vgshell-git` rebuild, and the result list names it skipped: `vgshell pkg run upgrade --manager pacman|aur --ignore <name>...`, or the `aurCommand` words with `--ignore <name>` per skipped package, AUR and repository, since those words may sync the system. Install anyway installs it. Either answer goes on with the run.
- The run removes the directory once it has read the verdict, and when it exits.

## Scope

Low free space is a warning, not a refusal, so a user with a small disk can still update.

The pipeline runs no migrations, keyring step, channels or ALPM guard: those are a distribution's work, and VGS is not a distribution. A run does not hold the system awake.
