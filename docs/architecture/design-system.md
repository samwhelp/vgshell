# One token table and one component library draw every surface

Read before touching a token, the theme judge, `Theme`, a component of `qs.Ui`, a plugin-owned look, a pointer, keyboard or focus path, a Settings field, or text a user reads.

## The approach

Every view meets the polish of Vercel's web app or a standard modern consumer app. This is the organization's user experience principle (owner, 2026-10-06).

Every value a surface draws with comes from one table, `shell/Commons/Tokens.js`, read as `Theme.<group>.<token>`. One pure judge, `shell/Commons/ThemeLogic.js`, resolves a theme document against the table, and `Theme` publishes each group frozen ([D015](../decisions/D015-tokens-are-a-judged-table.md)). The user's Appearance values, shell.json `appearance`, resolve with it once, over the theme ([D104](../decisions/D104-appearance-values-over-the-theme.md)).

The component library `qs.Ui`, listed in `shell/Ui/qmldir`, is the only code that turns a token into a drawn pixel. A screen composes its components and draws no control of its own. A control extends a `QtQuick.Templates` type ([D017](../decisions/D017-templates-and-path-icons.md)), and an overlay is a Quickshell `PopupWindow` anchored to the item that declares it ([D018](../decisions/D018-overlays-are-quickshell-popups.md)).

Each input behaviour has one owner in `qs.Ui`. `PointerCursor` draws the pointing hand, `TouchpadScroll` moves a view under a touchpad swipe, `KeyNav` moves through a composite, `FocusRing` shows focus, `ListCursor` draws a list's selection and `Pane` owns a container's inset. The Keyboard, Motion and Layout rules below govern them.

A plugin whose design must look the same under every theme owns its look through an `appearance` table. The same judge resolves it, fed only the theme's mode, accent, motion scale, interface font and raised surface colour, except the standard surface `GlassSurface` draws while glass is off ([D023](../decisions/D023-plugin-owned-appearance.md)). A plugin's Settings page is drawn from its manifest schema ([D032](../decisions/D032-settings-plugin-and-manifest-settings-convention.md)). Text a user reads states the result and the action the user takes.

## Why

One table is the one place a value changes, so a theme restyles every surface at once. A literal value or a private control is a second style system: a theme change misses it, and it draws states nobody checked in the Gallery.

One owner per input behaviour lets one check cover every site. A keyboard, pointer or touchpad user then gets the same behaviour on every screen, and no screen locks one of them out. A list cursor shared by rows prevents a hover fill and a keyboard highlight from showing different selections. One container inset keeps boxed children and unboxed text aligned, with equal side insets when content overflows.

A plugin-owned look names the theme values its design takes as its only inputs, so no other theme value can leak into it. The motion scale is one of them because it is the reduced-motion control, not styling.

A schema-built Settings page gives every plugin a full page with no UI code and the same rows. Runtime choices let that page offer discovered devices, accounts or models without deleting a stored value when an offer disappears. A user reads a label once. A diagnostic key, a reason code, a format syntax or a command asks for knowledge or work the shell should carry.

## Rules

### Tokens

- Do read every colour, font, metric, radius, opacity and duration from `Theme`. `scripts/check-design-tokens.py` refuses a literal in shipped QML under its `literal-*` rules, and an unknown `Theme` path under `token-unknown`.
- Do publish every top-level group of the table as a read-only property of `Theme`. `group-unpublished` in `scripts/check-design-tokens.py` refuses a group left out.
- Never give the table or the judge an import, a Qt object or I/O, so a script runs the shell's own judge. `scripts/test-theme-logic.js` runs both under node.
- Do keep the shipped layout scale on the 4 px grid. `GRID_EXCEPTIONS` in `scripts/test-theme-logic.js` names the permitted classes, and that test walks every length token. Keep row heights independent of the control size scale, so changing buttons does not resize every list.
- Do give a component whose text differs from a shared type role its own role in the `text` group, a scale of `font.size`, and never change a shared role for one component: `item` and `itemHint` draw fields, selects and list items, and a menu entry draws in `menuItem` and `menuItemHint`. `scripts/qml-tests/tst_label.qml` pins every role's size.
- Do keep the shipped theme and every catalog entry readable at the floors `ThemeLogic.readabilityShortfalls` states. `scripts/check-theme-contrast.js` judges them.
- Do measure a drawn hint at its native pixel size against the fill directly under it. Use the median RGB of repeated straight-stroke interiors across the line. Keep the same sample positions before and after. Exclude stroke edges and isolated extreme pixels. Apply the text readability floor to that sampled ink and fill; a passing token ratio alone does not prove that the drawn hint passes. `scripts/test-theme-logic.js` pins the hint's rendering margin; captured Settings pages prove the drawn result.
- Do keep a modal card the layer above the page its scrim dims, in every mode: its fill at least as light as the dimmed page or 3:1 against it, and its border 3:1 against it; where the scrim dims a wallpaper and no border colour holds 3:1 against it, the fill carries the layer at 3:1. `ThemeLogic.readabilityShortfalls` judges `dialog.background` and `dialog.border` over `color.scrim` on each resting surface.
- Do mark the item under the pointer with a line in its own colour where text sits on the scrim over a wallpaper: `carousel.hint` and `carousel.hintActive` are near one black or white there, so a colour change does not show. A closed tab under the pointer draws a line thinner than the open tab's (`Tabs` takes `hoverMark` for it) and a word draws underlined; the open tab's indicator draws `carousel.tabIndicator`, the accent where it reads 3:1 on that backdrop and `carousel.hintActive` where it does not, and a chosen word keeps `text.bodyStrong`'s weight.
- Do rest a failure or status line over a wallpaper on a solid plate, `carousel.failurePlate`, a theme surface, never on the scrim alone, and lead it with the danger mark, drawing both in `carousel.hintDanger`: the theme's danger where it reads 4.5:1 on the plate and the theme's text colour where it does not. `ThemeLogic.readabilityShortfalls` judges the line on the plate, which `scripts/check-theme-contrast.js` runs on every theme, and `scripts/test-theme-logic.js` pins the rule and the plate and mark in each view.
- Do centre an icon that leads a line of text on that line's capitals, half way between the baseline and the capital top (`Label.topForLeadingIcon`), never on the line box: the line box holds the descent, so its centre is under the capitals the eye levels the icon with. An icon beside exactly two lines centres on the block, as `ListItem` does. Beside three or more lines, or a block whose detail count changes with content, it centres on the first line's capitals through `Label.topForLeadingIcon`, so it stays beside the name it marks. Notification images and faces keep their media placement. `scripts/qml-tests/tst_label.qml` pins the placement, and `scripts/test-theme-logic.js` each site's call.
- Do draw rest, hover, pressed, focus, disabled and checked from their own tokens, each different from rest, and never draw hover or press on an item a click cannot change. A bar item or an icon button draws no hover fill. An icon button's glyph brightens from `color.textMuted` to the foreground. Keyboard focus keeps its focus ring, and press keeps a visible change. Review holds it; `scripts/qml-tests/tst_button.qml`, `tst_toggles.qml` and `tst_baritem.qml` pin the shipped controls.

### Appearance values

- Do resolve the user's Appearance values only in `ThemeLogic.withAppearance`, once, and read the result through `Theme`; a value the user has not set is the theme's. `scripts/test-theme-logic.js` pins that no value draws every package as before.
- Do set every token of a control from its one base by the fixed ratio in `ThemeLogic.APPEARANCE_RATIOS`, which holds every ratio, and apply a ratio to a user's value only. `scripts/test-theme-logic.js` pins each ratio.

- Do give a popover, a menu, a dialog or the OSD the radius `radius.glass` only while the user's `glass` is on and only where its radius would be 0, and keep a radius the theme or the user's Corner radius sets above 0. Never set `surface.radius` from it: a panel attached to the bar keeps the bar's square edge. `scripts/test-theme-logic.js` pins each case.

- Do set the interface font on `font.family.sans` and `font.family.caps` alone, so code and key names keep `font.family.mono`, and set no token from the terminal font, which the theme targets write ([themes.md](themes.md)). `scripts/test-theme-logic.js` pins both.

- Never take a colour as an Appearance value; colours stay the theme's ([D025](../decisions/D025-no-theme-override-layer.md)). Review holds it.
- Do draw a value that maps to a Hyprland option with `ValueSourceRow` ([D057](../decisions/D057-one-row-for-hyprland-mapped-values.md)). `scripts/qml-tests/tst_valuesourcerow.qml` pins its states.

### Appearance

- Do let a plugin own its look only through the `appearance` file its manifest names. `PluginLogic.validateManifest` refuses another shape, and `appearance-refused` in `scripts/check-design-tokens.py` refuses a table the judge refuses.
- Never read a `Theme` member other than `appearance` in such a plugin, and never name a path the look lacks. `theme-read` and `look-unknown` in `scripts/check-design-tokens.py` refuse both.
- Do bind the look once through `Theme.appearance`, read every value as `look.<path>`, and draw nothing on a null look. Review holds it.
- Never give a plugin-owned look a text size below the shell's smallest text role. `type-floor` in `scripts/check-design-tokens.py` refuses it.
- Do draw a text shadow only to lift light ink off dark glass; dark ink on a light card draws none. Key the shadow to the ink in one token, never a per-theme copy, as the notifications' `text.lift` does. `scripts/test-notifications-logic.js` pins it.
- Do hand every `qs.Ui` component a plugin-owned look draws with the look's own values; a component left on its defaults draws the shared tokens. `GlassSurface` takes only the look's fill, rounding and elevation, and while glass is off draws the standard surface. Gap: no check reads which values a plugin hands a component.

### Components

- Do give every input a minimum and maximum width from theme tokens. Enforce these bounds in `qs.Ui` components and the shared form row. Wide windows keep controls on the value column's start edge. Never set a width limit in a page or plugin.
- Do compose `qs.Ui` components, and never write a private control for something a component draws. Review holds it.
- Do draw a surface's background, a panel's, a flyout's, a popover's, a menu's, a tooltip's, a dialog's or an OSD's, with `Surface` or `GlassSurface`, handing it the surface's own token group as `standard`, so the user's `glass` value reaches it. `glass-bypass` in `scripts/check-design-tokens.py` refuses a background read of such a group outside it.
- Do add a new component to the Gallery in the same change, in every variant and state, with a focus example for a focusable control. `scripts/smoke/rows/gallery.sh` refuses a component `qmldir` lists that the Gallery lacks, and a missing focus example.
- Do disable a control the user cannot use now through its `disabledReason`, never `enabled: false` alone: one STE sentence that names the cause and the step, with no command and no internal word. The control stays a Tab stop, takes no click or key, draws faded, and shows the reason on hover and keyboard focus. A toggle that one user step unlocks also takes `unlock`, `{ label, run }`: a lock-open mark after it runs the step and shows the same reason. A panel header switch takes them as `switchDisabledReason` and `switchUnlock`. `scripts/qml-tests/tst_disabledreason.qml` pins the controls, and `scripts/check-disabled-reasons.py` lists every plugin site that binds `enabled` with no reason.
- Never give a decorative component, such as `VoiceOrb` or `QrMatrix`, a pointer handler, a process, a file, a cache or a secret store, so a passive layer that draws it stays input-free ([D026](../decisions/D026-passive-layers-are-a-capability.md)). `scripts/qml-tests/tst_voiceorb.qml` and `tst_qrmatrix.qml` pin it.

### Pointer

- Do declare `PointerCursor` in every element that takes a click, a plugin's `MouseArea` included, and never write `Qt.PointingHandCursor`. `scripts/check-pointer-cursor.py` refuses both under `cursor-missing` and `cursor-literal`; a `// pointer-cursor-exempt: <reason>` line exempts a click-away area or a scroll bar.
- Do set `acceptedButtons: Qt.NoButton` on every `Flickable`, `ListView` or `GridView`, so a mouse drag selects text instead of scrolling. `mouse-drag` in `scripts/check-pointer-cursor.py` refuses a view without it.
- Do declare `TouchpadScroll { view: <the view> }` in every view. `touchpad-scroll` in `scripts/check-pointer-cursor.py` refuses a view without it.

### Keyboard

- Never ship a click area without a keyboard path, or a focusable item without a focus indicator. `scripts/check-keyboard.py` refuses both, and `vgs-plugin check` runs it on a plugin tree.
- Do mark `// keyboard-path: <how>` or `// focus-indicator: <what>` only where a present mechanism supplies it; the marker exempts nothing missing. Review holds it.
- Do make a composite one Tab stop whose arrows move through `KeyNav`, and never let an arrow run an action. Review holds it; `scripts/test-key-nav-logic.js` pins `KeyNav`.
- Do let hosts own Escape and initial focus. Give a surface initial focus on its primary input, else its list, else its body, and never on an action that installs, removes or changes the system. Initial focus lands on the primary input, list or body with no ring. The ring appears after a keyboard navigation key. Review holds it.
- Never give the bar keyboard focus, except the focus grab that holds a widget drag until its release; a widget action has a global shortcut or a launcher path. Gap: no check reads the bar window's keyboard focus.
- Never give a passive layer the keyboard; the inbox is a toast's keyboard path. `scripts/smoke/rows/layers.sh` pins the layer host.

### Motion

- Do make every animation read a `motion` token, so `motion.scale` 0 stills the shell. `literal-duration` in `scripts/check-design-tokens.py` refuses a literal duration.
- Do stop an animation no duration drives, such as a shader clock, while `motion.scale` is 0. Review holds it.
- Do open and close a bar flyout with a Material container transform: fade plus a short slide from the anchor edge. `scripts/smoke/rows/surfaces.sh` pins the compositor placement and motion-scale stillness.
- Do give a list of selectable rows one `ListCursor`, and never a per-row hover fill beside it. Use the shared row entrance and pass a plugin-owned look's timings and plate into the cursor. `scripts/qml-tests/tst_listcursor.qml` and `tst_overlays.qml` pin it. A view's built-in highlight cannot replace the shared cursor: it supplies no easing curve and cannot serve rows in a `Column`.
- Never declare a `ListCursor` in a `Column`, `Row`, `Flow` or `Grid`, which would lay the shown plate out as a row and move every row; declare it beside the positioner. `cursor-positioner` in `scripts/check-pointer-cursor.py` refuses it.

### Layout

- Do put each surface title in the shared `Pane` title slot. Keep its subtitle or description with the title. Leave `Theme.stack.titleSpace`, at least one body line, after the whole title block. Never add a private title margin.
- Do give a sticky footer equal padding on every side. Keep a sticky header's divider outside the body's viewport. Use the shared `Pane` geometry or the container's padding token, never a separate bar offset. `scripts/qml-tests/tst_pane.qml` pins the rule.
- Do mark a scrolled body under a sticky header, or over a sticky footer, with the `Pane` divider alone: one line from frame to frame. A `ScrollArea` draws no edge line. Never draw a line under a sticky header in a surface, a nested `ScrollArea`'s edge line included; scroll the body in the `Pane`. `test_one_line_marks_each_scrolled_edge` in `scripts/qml-tests/tst_pane.qml` pins it.
- Do put a pending-changes row in the shared `Pane` footer, pinned to the bottom of the System or Shell & Plugins panel. Never put it in the scrolling body; review holds it.
- Do use a centred modal for a timed trial or a confirmation the user must see, such as Keep/Revert. Never use an inline card; review holds it.
- Do compose `Pane` for every window, dialog, panel, popover and overlay, and never write a second inset. Align boxed children and unboxed text to its content edge. `scripts/qml-tests/tst_pane.qml` pins the box.
- Do clear a rounded corner through `Inset.clearing` in `shell/Commons/Inset.js`, and never hand-pad for a curve. `scripts/test-inset.js` pins the rule.
- Do let `ScrollArea` mark at rest each edge content continues past by fading the content toward what lies behind it. Never draw a line or a tint over the fade band, and never hide the fade behind hover or a scroll. `scripts/qml-tests/tst_scroll.qml` pins it.
- Do keep a container's scroll bar inside its right inset strip. `scripts/qml-tests/tst_scroll.qml` pins the gutter with and without overflow.
- Do fit dialogs and popovers to their content up to their maximum height share, then scroll. `scripts/qml-tests/tst_pane.qml` pins the fitted height.
- Do animate a summoned flyout's or panel's card height through `SurfaceHeight`. A bar flyout takes the room below its anchor at open, keeps that size while its content fits in it, never shrinks while it shows, and masks input to its card; a panel's layer covers its screen and catches the presses outside its card. A popup anchored inside a window, such as `Popover`, `Menu`, `Select` or `Tooltip`, follows its content, since a client cannot read where that window sits. `scripts/qml-tests/tst_surfaceheight.qml` pins the card; gap: no check reads which hosts compose it.
- Do leave `stack.heading` above every section heading, from the lowest drawn pixel above it to the heading's capital top, through the shared `Section`, which reads what the item above draws (`Theme.inkBelow`) rather than its box. The first heading of a page takes no space of its own: a tab page starts `stack.page` under its tab strip (`TabPages`), as a window's page starts under its title. Never pad a section in a page. `scripts/qml-tests/tst_section_spacing.qml` pins it on three plugin pages and a Setup tab.
- Do draw a list of groups, such as a Status section's entries, the Setup tab's steps and keys, the Requirements rows or a log's records, with the shared `GroupList` of `qs.Ui`: groups `groupList.gap` apart by their line boxes, less how far a heading over its own group list starts its ink below its rows', so a drawn-ink reading of a gap may differ by the descent, and a hairline in each gap, centred between the lowest drawn pixel of the group above and the highest of the group below (`Theme.inkBelow`, `Theme.inkAbove`), the gap above a filled button included. Never space or divide such a list by hand. `scripts/qml-tests/tst_grouplist.qml` pins it from the rendered image.
- Do give a popover list no outer inset; its row fill meets the border and its row padding carries the text inset. `scripts/qml-tests/tst_overlays.qml` pins it.
- Do leave one blank row between blocks in a floating terminal: a cleared screen starts its first block on row 0, and one blank row stands under the logo. Draw each block through `bin/lib/tui.sh`, whose gap mark owns the blank row and takes the logo's row from `bin/vgshell-tui`; never print a blank line of your own. `scripts/test-tui.sh` pins it in "a header starts with one blank line", "two questions and a step after them share one blank line", "a step on a cleared screen starts on its first row" and "a header under the logo draws no blank line", and `scripts/test-vgshell-tui.sh` in "one blank row stands between the logo and the first header".

### Copy

- Do use an icon button's label as its tooltip: two or three words naming its action, with no explanation. Bar widget status readings keep their status text.
- Never let a tooltip cover a sibling label, or the control and buttons of the row it explains. An item with a label under it opens its tooltip to the right (`Tooltip`'s `side: "right"`, `IconButton`'s `tooltipSide`). A form row's explainer may cover its own row's hint, never another row's text, its control or its buttons: with no room past its control, or where it would clip the hint there, it opens under the row, over the hint from the hint's top (`side: "belowStart"`), on the value column beside a label focus ring that reaches the hint. That band draws a lifted fill with no outline, so it never reads as an empty input. That band is one line, the room the hint's top leaves above the next row. A row with no hint has no line of its own under it, and an explainer too long for one line of the value column would run onto the next row, so there the label opens nothing and the row's info button holds the explainer for its dialog. A form row's info button opens no tooltip, which would lie on the next row's label: a press opens its dialog. `scripts/qml-tests/tst_button.qml` pins both sides, and `scripts/qml-tests/tst_formrow.qml` and `tst_bindfield.qml` the row's.
- Do let the pointer and the keyboard reach a link in a tooltip. The tooltip stays open for `tooltip.delay` after the pointer leaves its item and while the pointer is on the tooltip. The item keeps the keyboard: Tab moves to the link and draws its focus ring, 2 px clear of its words as every link's is, and the item draws none while its link is current, so one ring shows where the next key goes; Enter, Return or Space opens it, a further Tab goes on to the next item, and Escape closes the tooltip. A tooltip with no link closes when the pointer leaves its item and takes no key. `scripts/qml-tests/tst_tooltip.qml` pins it, and `scripts/smoke/rows/bar.sh` the real pointer and keys.
- Do write text a user reads in ASD-STE100 Simplified Technical English. Name the result of a check or the action the user takes, never the internal operation. Review holds it.
- Do keep a plugin description to one or two short sentences with no feature list, and a hint to one sentence; longer help goes behind an `InfoButton`. Review holds it.
- Do end a Settings hint of one sentence without a full stop, and end each sentence of a longer hint with one: "Jarvis decision (2026-10-13, delegated authority): a one-sentence hint ends without a full stop; a hint of two or more sentences ends each sentence with one." `PluginLogic.validateManifest` refuses a hint that breaks it, and `scripts/test-plugin-logic.js` pins the judge.
- Do keep diagnostic keys, reason codes and command errors in the log, and map a plugin's own messages to a plain sentence before the plugin shows them. A user's own commands and their output stay unchanged. Review holds it.
- Never tell the user to run a command ([D061](../decisions/D061-no-manual-commands.md)). `scripts/check-user-commands.py` refuses the text.
- Do make text that names another VGS page, tab or section a link that opens it: use only the page reference form, `[words](page:<plugin id>/<tab>)`, which `LinkText` draws as the link and Settings opens from a description, a hint or a status text. A link's ring holds its words and the punctuation against their end, and stands 2 px, `focusRing.offset`, clear of them and their underline on every side. Text at rest keeps its spacing after a link; before one, a narrow no-break space is added only where the ring would touch the glyph before. `scripts/qml-tests/tst_linktext.qml` pins it. A bar item's tooltip draws the link too, and its widget opens the page through `frame.openPage`; any other tooltip draws the words alone. A plugin view opens the page through `shell.surfaces.openPage`, and a notice sends the reference's words, which a notice card draws as the link and a click on the card opens. A terminal line cannot link, so it names the button that opens the page. `page-reference` in `scripts/check-user-commands.py` refuses the plain words, `page-reference-target` refuses a literal target with no plugin directory, and `scripts/smoke/rows/settings.sh` pins the click.
- Do keep one clear pixel row between a link's underline and the lowest descender of its words, so no glyph touches the line: `LinkText`, `RowAction` and a notice card's page link (`ImageText`'s `underlined`) start the underline `Inset.underlineTop` under each baseline, a pixel under the font's descent read from its metrics. Never underline a link with `<u>`, which Qt draws where a descender meets it. `scripts/qml-tests/tst_linktext.qml`, `scripts/qml-tests/tst_rowaction.qml` and `scripts/qml-tests/tst_imagetext.qml` pin it.
- Follow [D075](../decisions/D075-consumer-features-need-no-developer-setup.md) when a setup step needs the user. Review checks the Settings path. Features without that path do not ship.

### Settings pages

- Do show a bind row with no info icon where it has a hint line, as a Settings key row has: its explanation opens in the shared tooltip over that line on label hover and keyboard focus while it fits one line there. A longer one, and that of a bind row with no hint line, as in Key Hints, opens in the row's info icon's dialog, since a tooltip there would lie on the bind under it.

- Do put a switch on its label's row in the value column, never below the label; review holds it.
- Do give a plugin page one tab per kind of item, and never draw an item on two: Settings holds what a user chooses, Setup holds what a user does, and Details holds what a user reads. Show Setup, between Settings and Details, only for a plugin with a setup step, a stored key, a setup screen or a tool to install or update. `scripts/test-settings-steps.js` pins the tab and each item's place, and `scripts/qml-tests/tst_settings_setup.qml` the page.
- Do draw a status entry whose manifest declares an action as a step on Setup under every value, never on Details: in the Setup section for an entry of no group, else in a section titled with its group. Details draws no action of a status entry. Count such a step outside the `Setup` group and the keyed groups toward Setup needed only while it is open and its value offers its action. `scripts/test-settings-steps.js` pins the judge and `scripts/qml-tests/tst_settings_setup.qml` the page.
- Do order the Setup tab's steps by what the user can still do: open steps first, then steps that are not done and offer their action, an optional one included, then the done steps, each in manifest order. A step that is not done and offers no action, such as one that waits on another step, ranks with the done steps, since the user cannot act on it now. Draw a setup screen a status entry declares only beside that entry's row, while its value offers it, so a done step offers no setup action anywhere; draw a listed screen no entry declares under the labelled More setup row only when its manifest marks it `setup`, else in the Actions row of Details, so a screen that sets nothing up gives the page no Setup tab. `scripts/test-settings-steps.js` pins both.
- Do draw a plugin's Requirements section, every tool with its state and the one install or update action, on one tab: Setup when the page has that tab, else Details. While every tool to install or update is optional, the action is a row action under the Optional tools label, never the page's primary action. A tool to install or update gives the page its Setup tab, so Details never draws that action. `scripts/qml-tests/tst_settings_setup.qml` pins it.
- Do give each Requirements row one state in its chip: Present in the success tone, Missing in the danger tone, Optional in the info tone for a missing optional tool, and Outdated in the warning tone, optional or not. The purpose line under the chip says what the tool adds. `scripts/qml-tests/tst_settings_setup.qml` pins it.
- Do mark a plugin that is on in the Plugins list: a Setup needed chip while a setup step is open or a required tool is missing or outdated, and a warning icon in `color.warning` while an optional tool is missing. A row with the chip opens on Setup and the icon opens Setup; every other way to a page opens Settings. Never mark a plugin that is off. `scripts/test-settings-steps.js` pins the judge and `scripts/qml-tests/tst_settings_setup.qml` the row.
- Do set a key or token a plugin stores on its Setup tab, one line per key with its chip: in the Setup section, or in the own section of the status group that lists it, beside that group's states. A key the core stores takes Add key on its line while none is stored, and Replace and Remove while one is. `scripts/test-settings-steps.js` pins the placement and `scripts/qml-tests/tst_grouplist.qml` the line.
- Do keep each setting in its settings group. If a setting applies to the whole group, say so in its help instead of placing it above the group; review holds it.
- Do give bar widgets with like settings one order: a widget that offers `layout` groups every field, leads with the Readings group, and starts it with the shared fields it offers in the order `layout`, `labelStyle`, `refreshSeconds`. `bin/lib/check-manifests.js` refuses another order.
- Do declare a plugin's settings in its manifest schema, and never ship page code for its Settings page. `scripts/test-plugin-logic.js` pins the schema.
- Never make a user type a library's format syntax. Declare `presets` or `optionsFrom`, and judge a format string before writing it. `PluginLogic.validateManifest` refuses a string setting without either, and `scripts/test-setting-values.js` holds the format judge.
- Do feed `optionsFrom` from a `choices` status entry of the same plugin, with stable ids and labels. The first offered choice stands for the unset value and reads as its own label, so offer first what the unset value resolves to, such as a "System default" entry. A setting whose unset value means nothing is chosen declares `placeholder`, and the select reads it instead of an offer. Keep a configured id that leaves the offers and show it as unavailable, or under Custom… when the entry declares `allowCustom`; a `hideEmpty` field alone draws nothing while nothing is offered, whatever is configured. `scripts/test-plugin-logic.js` pins the schema and `scripts/test-plugin-status.js` the `settingChoices` model.
- Do use the shared Settings row height token for every inline setting, so rows stay aligned. Review holds it.
- Do write a setting's label to fit the label column: it wraps there and never draws an ellipsis in any theme or scale, and at the default theme it fits two lines of the column, beside its info mark when it has one. Give a label that needs more words a one-sentence `tooltip`, which the label shows on hover and keyboard focus; longer help stays in `info`. `PluginLogic.validateManifest` refuses a longer label, `scripts/test-plugin-logic.js` pins the judge, and `scripts/qml-tests/tst_settingfield.qml` holds the judge's line count to the drawn label and pins the tooltip.
- Do draw the action of a key/value row as a `RowAction` right after the row's value: accent body text over an underline. Never put a boxed `Button` in such a row; a filled primary `Button` stands in a row only as the page's one main action: the Setup tab's first offered setup step that is no danger, an optional one only while no required step is open, else Install all missing, which `scripts/test-settings-steps.js` pins. Set two or more actions of one row in `RowActions`, `rowAction.gap` apart. `scripts/qml-tests/tst_rowaction.qml` pins the control and the gap; review holds its placement.
- Do lead every danger action with its trash mark, in the theme's danger colour, so it reads apart from an accent action by more than colour; `scripts/qml-tests/tst_rowaction.qml` pins it.
- Do put a row's description, its lines, hint or error, on its own lines under the row's value, followed by the group space, `stack.group`, before the next row. `Theme.subTextRoom` gives that space in `Field`, `FormRow` and `SettingField`; `scripts/qml-tests/tst_spacing.qml`, `tst_formrow.qml` and `tst_settingfield.qml` pin it.

## The canonical example

`shell/Ui/controls/IconButton.qml` is a control that meets every rule above. Copy it. For a plugin-owned look, copy `shell/plugins/vgs.launcher/Appearance.js` with `Launcher.qml`.

## Revisit when

A value a surface needs cannot be a token; a surface needs an input or keyboard model the shared owners cannot express; a plugin-owned look needs a sixth theme input, or a theme must restyle it after all; a Settings field needs a control the manifest schema cannot declare. A child must draw outside its container inset, a list needs several selection plates, runtime discovery outgrows the bounded choices list, or the owner changes the layout grid.

## Not governed

The theme package format, apply and targets, which are [themes.md](themes.md). The compositor-side capture of keys, which is [hyprland.md](hyprland.md). Each component's properties, signals and key handling, which are its file header, its test under `scripts/qml-tests/` and the vgs-plugin skill's API reference. A plugin-owned look's own values, which its appearance table holds. Developer logs, code comments, developer documentation and machine-readable output, which stay technical; a Gallery preview may name the component, property or state it shows.
